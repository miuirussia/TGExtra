# Обновление патчей TGExtra для Telegram и Swiftgram

[English version](UPDATING.en.md)

Руководство для человека, который умеет запускать команды в терминале, но раньше
не работал с ассемблером. Здесь описано обновление профилей совместимости TGExtra
под новые **iOS IPA** Telegram и Swiftgram.

Начните с автоматического обновления. Читать машинный код понадобится, только
если новая сборка не проходит существующие проверки. Тогда нужно выяснить,
что изменилось в программе, и подтвердить, что патч по-прежнему работает правильно.
Замена номера версии или хеша сама по себе такую совместимость не создаёт.

Текущие эталонные сборки в репозитории: **Telegram 13.2.1 (36542)** и
**Swiftgram 13.1.3 (360, `app.swiftgram.ios`)**. Это проверенные исходные точки,
а не утверждение о совместимости со всеми более новыми версиями.

## Что именно обновляется

IPA — архив с приложением. Внутри находятся исполняемый файл, библиотеки,
ресурсы и `Info.plist` с данными о приложении. Исполняемые файлы iOS имеют формат
**Mach-O**. Скомпилированный код внутри них можно представить в виде команд
ассемблера: это называется **дизассемблированием**.

В TGExtra участвуют несколько разных частей:

| Часть | Содержимое и назначение |
| --- | --- |
| TGExtra DEB | Сам твик: настройки, обработка сообщений, реализация функций |
| `Patches/<id>/patch.json` | Профиль: как найти нужный код, проверить его и изменить |
| `payloads/*.c` | Исходники небольших адаптеров между приложением и твиком |
| `payloads/*.bin` | Скомпилированные адаптеры, которые вставляются в приложение |
| `.ipatch` | Пакет для движка: профили, адаптеры и, в итоговом пакете TGExtra, соответствующий DEB |
| `Tools/update_patches.py` | Общий скрипт попытки обновления профилей |

**Профиль совместимости** описывает проверенный участок кода. Адрес функции
между сборками может измениться, поэтому движок ищет её по признакам:
отпечатку команд, структуре Swift, связям между функциями и числу вызовов.

**Payload**, или адаптер, — небольшой фрагмент кода, через который начинает
проходить нужный вызов. Обычно он обращается к TGExtra, а при отсутствии твика
передаёт управление исходной функции. Swiftgram Pro использует отдельную вставку,
которая меняет сохраняемое значение и не требует TGExtra во время выполнения.

В репозитории есть четыре семейства:

| Семейство | Каталог | Что нужно при обновлении |
| --- | --- | --- |
| Native TL Decoder | `Patches/native-tl-v1` | Проверить парсеры TL и точки их вызова; обновить также runtime matcher |
| Rust MTProto Bridge | `Patches/rust-abi5-*` | Проверить функции Rust, ABI, привязку сессии и вызовы; профиль создаётся для каждого совместимого клиента |
| Secret Chat Protection | `Patches/secret-chats-v1` | Проверить пять точек перехвата и исходные функции; генератору нужны обе IPA |
| Swiftgram Pro | `Patches/swiftgram-pro-status-v1` | Проверить метаданные Swift и декодер; автоматического переноса изменённого кода нет |

Первые три входят в обязательный компонент **TGExtra**, с идентификатором
`required`. **Swiftgram Pro** — отдельный необязательный компонент
`swiftgram-pro`, по умолчанию выключенный.

Обновление этих профилей не исправляет автоматически изменения интерфейса
Telegram, UI hooks или схемы API. Например, исчезнувшая кнопка настроек может
требовать изменения исходников твика при полностью совместимых бинарных патчах.

## Подготовка рабочего места

### Система и инструменты

Для описанного процесса используйте macOS с инструментами Xcode. На Intel можно
генерировать патчи и выполнять часть проверок. Для тестов, исполняющих ARM64-код,
нужен Mac с Apple Silicon. Полный набор тестов также использует SDK Mac Catalyst
и препроцессор Logos; подготовка сборочного окружения описана в
[основном README](../README.md#building).

Проверьте инструменты:

```sh
python3 --version
git --version
xcode-select -p
xcrun --find clang
xcrun --find swiftc
```

Если инструменты командной строки Xcode отсутствуют:

```sh
xcode-select --install
```

Для генерации адаптеров нужен Apple Clang: скрипты вызывают его через `xcrun`.
Наличие обычного `clang` в Linux не заменяет это окружение.

Понадобится также CLI **ipatch с поддержкой формата v4**. Ссылки для загрузки
есть в [разделе установки](../README.md#patching-an-ipa-with-ipatch).
Для Secret Chats движок должен поддерживать поле `dylib` у `import_stub`.

Сохраните CLI, например, как `~/Tools/ipatch`, и выполните:

```sh
chmod +x "$HOME/Tools/ipatch"
export IPATCH_ENGINE_CLI="$HOME/Tools/ipatch"
```

Переменная действует в текущем окне терминала. В новом окне задайте её снова.
Путь в примере можно заменить на свой.

### Исходные приложения

Нужны оригинальные **расшифрованные** IPA без уже встроенных твиков и патчей.
Просто переименовать ZIP или снять подпись недостаточно: код приложения должен
быть доступен для чтения. Если Mach-O зашифрован, генератор остановится.

Используемые генераторы рассчитаны на **thin generic arm64**: один вариант
архитектуры в файле. `arm64e` и FAT-файл с несколькими архитектурами не являются
подходящей исходной точкой для этих генераторов. Сам движок умеет применять
Rust-профили к arm64-срезу поддерживаемого FAT-файла; возможности генератора и
движка здесь различаются.

Положите новые IPA в `packages/`. В следующих командах используются условные имена:

```text
packages/Telegram_new.ipa
packages/Swiftgram_new.ipa
```

Заменяйте их своими именами во всех командах. Старые эталонные IPA сохраните
отдельно: они понадобятся для сравнения и проверки прежней совместимости.

Запишите для каждого файла версию, build number и bundle ID. Их можно прочитать
без распаковки всего архива:

```sh
python3 - packages/Telegram_new.ipa packages/Swiftgram_new.ipa <<'PY'
import plistlib
import sys
import zipfile

for filename in sys.argv[1:]:
    with zipfile.ZipFile(filename) as archive:
        entries = [name for name in archive.namelist()
                   if name.startswith('Payload/') and name.count('/') == 2
                   and name.endswith('/Info.plist')]
        if len(entries) != 1:
            raise SystemExit(f'{filename}: ожидался один основной Info.plist')
        info = plistlib.loads(archive.read(entries[0]))
    print(filename)
    for key in ('CFBundleShortVersionString', 'CFBundleVersion', 'CFBundleIdentifier'):
        print(f'  {key}: {info.get(key)}')
PY
```

Для идентификации конкретных входных архивов сохраните их SHA-256:

```sh
shasum -a 256 packages/Telegram_new.ipa packages/Swiftgram_new.ipa
```

Этот хеш обозначает конкретный архив. Он не заменяет отпечатки функций в профилях.

### Отдельная ветка

Откройте терминал в корне TGExtra: там должны находиться `Tools`, `Patches`,
`Sources` и `Tests`.

```sh
git status --short
git switch -c patches/update-clients
```

Если уже есть незавершённые изменения, сначала сохраните свою работу привычным
способом, чтобы отличать её от результатов генерации. Каталог `packages/`
игнорируется Git: входные IPA не требуется коммитить.

## Обновление без знания ассемблера

### Сначала проверить без записи

```sh
python3 Tools/update_patches.py \
  --telegram packages/Telegram_new.ipa \
  --swiftgram packages/Swiftgram_new.ipa \
  --engine "$IPATCH_ENGINE_CLI" \
  --check
```

Скрипт работает во временных копиях. С `--check` он сравнивает сгенерированные
исходники с репозиторием, сохраняя рабочие файлы без изменений. Отсутствующие
игнорируемые `.bin` в этом режиме не считаются изменением исходников.

Возможные сообщения:

| Сообщение | Значение и действие |
| --- | --- |
| `up to date` | Получившиеся исходники уже совпадают с репозиторием |
| `generated files differ` | Генерация прошла, но есть изменения; для их сохранения повторите запуск без `--check` |
| `unrecognized`, `ambiguous`, `ABI changed` | Код или его распознавание требуют разбора; переходите к соответствующей ошибке ниже |
| `No Rust runtime` | Rust в клиенте не найден; новый Rust-профиль не создаётся, используются имеющиеся MtProtoKit hooks |
| `skipped` | Этот этап не проверялся; прочитайте указанную причину |

Коды завершения:

- `0` — все выполненные попытки успешны;
- `1` — хотя бы одна попытка неуспешна, включая найденные отличия при `--check`;
- `2` — ошибка аргументов или неоднозначный выбор IPA.

Код `0` не означает, что выполнены пропущенные этапы или пройдены проверки
на телефоне.

### Сохранить результат

Если требуется записать сгенерированные профили, повторите команду без `--check`:

```sh
python3 Tools/update_patches.py \
  --telegram packages/Telegram_new.ipa \
  --swiftgram packages/Swiftgram_new.ipa \
  --engine "$IPATCH_ENGINE_CLI"
```

Скрипт последовательно пытается:

1. Сгенерировать общий Native TL и проверить его на обоих клиентах.
2. Сгенерировать Rust-профиль отдельно для каждой IPA, если в ней есть Rust.
3. Сгенерировать Secret Chats по обеим IPA.
4. Проверить существующий Swiftgram Pro с включённым необязательным компонентом.

С `--engine` каждый полученный профиль должен пройти планировщик движка до
копирования в рабочий каталог. Эта проверка вычисляет изменения, но не применяет
их к исходной IPA.

**Изоляция действует на отдельную попытку.** Если Native TL не прошёл,
Rust всё равно может успешно обновиться и записаться. Неуспешная попытка
сохраняет свой профиль в прежнем состоянии. Весь запуск не является одной общей
транзакцией с откатом всех успешных этапов. Исходные IPA скрипт не меняет.

### Посмотреть изменения

```sh
git status --short
git diff --stat
git diff -- Patches Sources/tgapiC/NativeTLProfile.inc
```

Проверьте смысл изменений:

- Новый каталог `rust-abi5-...` может быть ожидаемым новым профилем. Старые
  Rust-профили при обновлении сохраняются.
- `Sources/tgapiC/NativeTLProfile.inc` должен меняться вместе с соответствующим
  обновлением Native TL: это часть поиска парсеров внутри твика.
- Изменённые размеры и relocations адаптеров должны соответствовать результату
  компиляции. Разные версии Apple Clang могут давать разные бинарные адаптеры
  и идентификаторы Rust-профилей.
- Ослабление проверок, исчезновение проверок исходной функции или случайное
  добавление bundle ID не являются обычной частью переноса.

Затем снова выполните команду с `--check`. Если она сообщает о совместимом,
но отличающемся результате после только что выполненной генерации, сначала
разберите причину невоспроизводимости.

### Когда доступна только одна IPA

Можно явно передать один клиент и указать для автоматического поиска пустой
каталог, чтобы скрипт не подхватил второй клиент из `packages/`:

```sh
mkdir -p packages/empty-discovery
python3 Tools/update_patches.py \
  --packages packages/empty-discovery \
  --telegram packages/Telegram_new.ipa \
  --engine "$IPATCH_ENGINE_CLI"
```

Для Swiftgram замените `--telegram` на `--swiftgram`. При таком запуске
Secret Chats будет пропущен: его генератору нужны обе IPA. При обновлении общего
Native TL отдельно проверьте сохранение совместимости со вторым клиентом.

Без `--engine` и без переменной `IPATCH_ENGINE_CLI` генерация тоже возможна,
но проверки движком и Swiftgram Pro пропускаются. Для подготовки релиза выполните
их отдельно. Сам по себе успешный запуск Python этого не подтверждает.

## Проверки и сборка IPA

### Пересобрать адаптеры

```sh
python3 Tools/build_payloads.py
python3 Tools/build_payloads.py --check
```

Первая команда создаёт `.bin` из исходников C и обновляет связанные размеры,
relocations и при необходимости идентификаторы Rust-профилей. Вторая проверяет
соответствие. Пересборка не делает неизвестный код Telegram совместимым:
она компилирует уже описанные адаптеры.

Для проверки свежего checkout сначала нужна первая команда: `.bin` не хранятся
в Git. Общий запуск `bash Tests/run.sh` выполняет пересборку самостоятельно.

### Выполнить тесты

На подготовленном macOS:

```sh
export IPATCH_ENGINE_CLI="$HOME/Tools/ipatch"
export SWIFTGRAM_REFERENCE_IPA="$PWD/packages/Swiftgram_new.ipa"
bash Tests/run.sh
```

Для отдельной проверки патчей после пересборки адаптеров:

```sh
python3 Tests/update_patches.py
python3 Tests/native_tl_profile.py
python3 Tests/rust_portable.py
python3 Tests/secret_chats.py
python3 Tests/swiftgram_pro_ipatch.py
python3 Tests/ipatch_packaging.py
```

Тесты используют переменные окружения, заданные выше. `SWIFTGRAM_REFERENCE_IPA`
задаёт IPA для проверки Pro, но **не переключает все остальные тесты**.
Часть проверок Native TL, Rust и Secret Chats ищет фиксированные эталонные имена
`packages/Telegram_v13.2.1.ipa` и `packages/Swiftgram_v13.1.3_360.ipa`.
Некоторые проверки при отсутствии этих файлов просто не выполняют сравнение.

Поэтому сохраните настоящие старые эталоны под их исходными именами. Новую IPA
обязательно проверьте через `update_patches.py --engine` и через итоговый пакет
ниже. При постоянном добавлении нового эталона расширьте соответствующие тесты
с его настоящим именем. Переименование новой версии в старую скрывает,
какая сборка фактически проверена.

Читайте сообщения `skipped`: отсутствие CLI, IPA или Apple Silicon означает,
что соответствующая проверка не состоялась. Успешные тесты с пропусками
не равнозначны исполнению всех адаптеров и проверке обоих новых клиентов.

### Собрать итоговый пакет

Используйте DEB, собранный из той же версии исходников, что и профили. Это
особенно важно после изменения runtime matcher или контрактов адаптеров.

```sh
python3 Tools/package_ipatch.py \
  --deb packages/TGExtra.deb \
  --patches Patches \
  --output packages/TGExtra-updated.ipatch
```

`packages/TGExtra.deb` — условное имя: подставьте реальный DEB нужного варианта
установки. Пакет включает профили из `Patches` и соответствующие им адаптеры.
Если нужен полный локальный цикл сборки DEB и ipatch для трёх вариантов
установки, используйте `./build-arm64.sh` по основному README.

### Проверить итоговый план для новых клиентов

```sh
"$IPATCH_ENGINE_CLI" -dry-run -explain \
  -ipa packages/Telegram_new.ipa \
  -package packages/TGExtra-updated.ipatch

"$IPATCH_ENGINE_CLI" -dry-run -explain \
  -ipa packages/Swiftgram_new.ipa \
  -package packages/TGExtra-updated.ipatch
```

Отдельно проверьте Swiftgram с включённым Pro:

```sh
"$IPATCH_ENGINE_CLI" -dry-run -explain \
  -ipa packages/Swiftgram_new.ipa \
  -package packages/TGExtra-updated.ipatch \
  -feature packages/TGExtra-updated.ipatch:swiftgram-pro
```

Префикс у `-feature` должен совпадать с путём, указанным в `-package`.
Успех с Pro по умолчанию выключенным не проверяет совместимость Pro.

В плане должны разрешаться ожидаемые профили данного клиента, точки правок,
адаптеры и создаваемые метаданные. Например, для соответствующих профилей это
`TGExtraNativeTL.plist`, `TGExtraRustBridge.plist` и `TGExtraSecretChats.plist`.
Отсутствие Rust-метаданных нормально только для клиента без Rust.
Неожиданно пустой план или отсутствие нужного семейства требуют разбора.

### Применить к копиям и установить

После успешных проверок:

```sh
"$IPATCH_ENGINE_CLI" -apply \
  -ipa packages/Telegram_new.ipa \
  -package packages/TGExtra-updated.ipatch \
  -output packages/Telegram-TGExtra.ipa

"$IPATCH_ENGINE_CLI" -apply \
  -ipa packages/Swiftgram_new.ipa \
  -package packages/TGExtra-updated.ipatch \
  -output packages/Swiftgram-TGExtra.ipa
```

Чтобы включить Pro, добавьте к Swiftgram-команде тот же `-feature`, что выше.
При необходимости совместимости с sideload добавьте `-sideload`.
Результат имеет ad hoc подпись; подпишите и установите его своим инструментом
для установки IPA. Детали установки есть в основном README.

Для каждого повторного эксперимента берите оригинальную IPA. Для выключения
Pro также пересоберите IPA из оригинала с компонентом Pro выключенным.

## Частые ошибки

| Сообщение или симптом | Что проверить |
| --- | --- |
| `no reference IPAs` | Путь к IPA, её наличие и параметры `--telegram` / `--swiftgram` |
| `multiple telegram IPAs` / `multiple swiftgram IPAs` | Передайте нужный файл явно; не полагайтесь на выбор последней версии |
| `engine is not executable` | Путь к CLI, права `chmod +x`, соответствие CLI системе Mac |
| `xcrun` отсутствует или не находит Clang | Установку и выбор инструментов Xcode |
| `image is encrypted` | Нужна расшифрованная IPA; изменение fingerprint это не исправит |
| `expected a thin ... Mach-O` | Не попал ли FAT-файл вместо thin arm64 |
| `only generic arm64 is supported` | Архитектуру исследуемого файла; arm64e требует отдельной работы |
| `expected one native TL image` / `expected one TelegramCore image` | Содержимое IPA и путь к framework; после переименования библиотеки может потребоваться обновить поиск в генераторе |
| `unrecognized ...: 0` | Совпадений нет: проверьте входной файл, затем изменение кода, границ функции или отпечатка |
| `ambiguous` или несколько совпадений | Найдено несколько кандидатов: нужны дополнительные признаки для однозначного выбора |
| `unrecognized Rust ABI/buffer cluster` | Изменился Rust engine или проверяемая группа функций; требуется разбор ABI |
| `unsupported call count` / `expected one root call` | Изменились вызовы, появилась новая ветка или функция была встроена компилятором |
| `original target` / `import binding` | Изменилась вызываемая функция, stub, импортируемый символ или библиотека |
| `generated files differ` при `--check` | Есть воспроизводимые изменения; сравните запуск без `--check` и diff |
| `stale C payload` / `stale ... metadata` | Пересоберите через `Tools/build_payloads.py`, затем изучите изменения |
| `Swift witness adapter must remain exactly 20 bytes` | Изменился Pro-адаптер или вывод компилятора; нужно проверить его инструкции и контракт вставки |
| `arm64 branch is out of range` | Адаптер слишком далеко от точки перехода; нужно проверить размещение и relocations |
| План прошёл, приложение падает | Проверить сохранение регистров, стек, владение памятью, подпись и фактический путь выполнения на устройстве |

При ошибке распознавания сначала исключите неверный входной файл. Затем
сравнивайте старый и новый код. Ни номер версии, ни одинаковое имя функции
не доказывают одинаковый ABI.

## Основы ARM64 для чтения патчей

### Регистры и память

Регистр — маленькая ячейка внутри процессора. В командах ARM64 регистры общего
назначения называются `x0`–`x30` и имеют размер 64 бита. Имена `w0`–`w30`
обозначают младшие 32 бита тех же регистров. Запись в `w0` обнуляет старшие
32 бита `x0`: замена `x0` на `w0` может изменить смысл операции.

Для чтения этих патчей полезны следующие ориентиры:

| Регистр | На что смотреть |
| --- | --- |
| `x0`–`x7` | Первые простые целочисленные аргументы в обычном C ABI; `x0` часто содержит результат |
| `x8` | Может нести адрес для косвенного результата; в проверенном Pro witness это адрес выходного значения на входе |
| `x19`–`x28` | Сохраняемые регистры в обычном ABI; вставка не должна разрушить значения, нужные окружающему коду |
| `x20` | В Swift может содержать `swiftself`, то есть контекст вызова |
| `x21` | В проверяемых Swift-адаптерах используется для `swifterror`, то есть состояния ошибки |
| `x29` | Обычно указатель текущего кадра стека |
| `x30`, или `lr` | Адрес возврата после вызова |
| `sp` | Указатель стека |
| `xzr` / `wzr` | При чтении дают ноль |

Это ориентиры, а не готовая сигнатура произвольной Swift-функции. Аргументы
могут передаваться через стек, несколько регистров, указатели и отдельные
регистры для чисел с плавающей точкой. Роли регистров общего ABI описаны в
[стандарте Arm AAPCS64](https://github.com/ARM-software/abi-aa/blob/main/aapcs64/aapcs64.rst).
Для Apple есть [дополнения к ARM64 ABI](https://developer.apple.com/documentation/xcode/writing-arm64-code-for-apple-platforms).

**ABI** — правила взаимодействия скомпилированного кода: где лежат аргументы
и результат, какие регистры сохраняются, как представлен объект и кто освобождает
память. Совпадения названий и размеров функций недостаточно для подтверждения
этих правил. Особенности Swift объясняет
[документ о Swift calling convention](https://github.com/swiftlang/swift/blob/main/docs/ABI/CallingConvention.rst).

### Минимальный набор инструкций

В этих примерах первый операнд обычно обозначает место результата.
`#` перед числом означает непосредственное числовое значение.

| Команда | Смысл |
| --- | --- |
| `mov x0, x1` | Скопировать значение `x1` в `x0` |
| `mov x8, #2` | Положить число 2 в `x8` |
| `ldr x0, [x19]` | Прочитать 8 байт памяти по адресу из `x19` в `x0` |
| `str x0, [x19]` | Записать 8 байт из `x0` по адресу из `x19` |
| `ldr w0, [x19, #8]` | Прочитать 4 байта по адресу `x19 + 8` |
| `stp` / `ldp` | Сохранить / загрузить пару регистров |
| `add` / `sub` | Сложить / вычесть; часто используются при работе со стеком |
| `cmp x0, x8` | Сравнить значения, записав результат сравнения во флаги процессора |
| `cbz x21, target` | Перейти к `target`, если `x21` равен нулю |
| `cbnz x21, target` | Перейти, если `x21` не равен нулю |
| `tbz` / `tbnz` | Перейти в зависимости от значения отдельного бита |
| `csel x0, x0, x8, ge` | Выбрать прежний `x0`, если предыдущее сравнение дало signed «больше или равно»; иначе выбрать `x8` |
| `b target` | Перейти без изменения адреса возврата |
| `bl target` | Вызвать код, сохранив адрес следующей инструкции в `x30` |
| `blr x16` | Вызвать код по адресу из `x16`, сохранив адрес возврата |
| `ret` | Вернуться по адресу из `x30` |
| `adrp` с последующей `add` или `ldr` | Часто используется для получения адреса данных или доступа к ним |

У `b` и `bl` разный смысл. Если вставка продолжает существующую функцию,
лишнее изменение `x30` может нарушить возврат. Адаптер, завершающийся
`b Original`, может передавать управление исходной функции с сохранением
адреса возврата исходного вызывающего кода: это хвостовой переход.

Для значений со знаком используются условия `ge`, `lt` и другие. Для беззнаковых
значений условия отличаются. Например, Pro-адаптер обрабатывает `Int64`,
и выбор signed-сравнения влияет на отрицательные значения.
Описание инструкций есть в [руководстве Arm по A64](https://developer.arm.com/documentation/102374/latest/).

### Адреса и смещения

В коде часто встречаются шестнадцатеричные числа: `0x18` равно 24,
`0x1c` равно 28. В JSON число `24` без префикса обычно записано в десятичной форме.

Одна машинная инструкция A64 занимает **4 байта**. Смещение `+24` означает
шесть инструкций от начала функции. Это справедливо для участка инструкций,
но не означает, что любые данные в файле нужно делить по четыре байта.

Различайте:

- **VA** — виртуальный адрес в образе, который показывает дизассемблер;
- **file offset** — позицию байта внутри Mach-O;
- **offset относительно функции** — расстояние от её начала до инструкции;
- **адрес в запущенном процессе** — он может отличаться из-за ASLR.

Для участка внутри файловой части сегмента:

```text
file_offset = segment.fileoff + (VA - segment.vmaddr)
```

Нельзя передать VA в редактор файла как готовую позицию байта. Участки zero-fill
вообще могут иметь адрес в памяти без соответствующих байтов в файле.
Для преобразований в утилитах проекта используется `MachO.offset()`.

### Отпечатки функций

**Fingerprint** — отпечаток команд функции после определённой нормализации.
Нормализация убирает часть различий, возникающих при изменении размещения кода
и данных. Она сохраняет те различия, которые алгоритм считает значимыми.
Поэтому перенос адресов иногда совместим с прежним профилем, а изменение
одной константы может потребовать нового.

В проекте существуют разные хеши:

| Вид | Где используется |
| --- | --- |
| SHA-256 всего архива или файла | Идентификация точного входа; также защита конкретного файла после планирования движком |
| Старый review fingerprint, `MachO.fingerprint()` | Допуск исходного кода в генераторах Native TL и Rust |
| `arm64-reloc-v1`, `MachO.portable_fingerprint()` | Переносимые проверки движка; также reviewed-проверки Secret Chats |

Эти значения нельзя взаимозаменять. В частности, результат обычного `shasum`
не подходит вместо `arm64-reloc-v1`, а старый review hash нельзя просто пометить
названием нового алгоритма.

### Якоря и relocations

**Anchor**, или якорь, — именованная найденная точка. Например, `decode`
может обозначать функцию декодирования, а `original.delete` — проверенную
исходную функцию удаления. `offset_bytes` задаёт смещение от этой точки.

**Relocation** описывает, как движку подставить адрес после размещения адаптера.
Например, в исходном профиле может стоять заготовка команды `b`, а конечную
дальность перехода движок вычислит при применении. Скопированные из одной
сборки байты перехода могут вести по неверному адресу в другой сборке.

## Поиск кода в новой версии

Этот раздел нужен, если автоматический перенос остановился на изменении кода.
Сначала исследуйте старую поддерживаемую IPA: у неё уже известны смысл патча
и проверяемые функции. Затем сравнивайте соответствующий код новой версии.

### Извлечь файлы для чтения

Создайте рабочую папку вне Git, например во временном каталоге macOS:

```sh
PATCH_REVIEW_DIR="$(mktemp -d "${TMPDIR:-/tmp}/tgextra-review.XXXXXX")"
export PATCH_REVIEW_DIR
mkdir -p "$PATCH_REVIEW_DIR/old" "$PATCH_REVIEW_DIR/new"
unzip -q packages/Telegram_v13.2.1.ipa -d "$PATCH_REVIEW_DIR/old"
unzip -q packages/Telegram_new.ipa -d "$PATCH_REVIEW_DIR/new"
```

Это пример для Telegram. Для Swiftgram используйте его старую и новую IPA
в отдельном рабочем каталоге. Здесь `$(...)` сохраняет путь, возвращённый
`mktemp`; исходные IPA остаются на месте.

Найдите нужный файл:

```sh
rg --files "$PATCH_REVIEW_DIR/new/Payload" \
  | rg 'TelegramCoreFramework.framework/TelegramCoreFramework$'
```

Для Native TL и Secret Chats генераторы сейчас ожидают именно этот framework.
Rust-генератор ищет подходящий образ по признакам движка; имя framework
само по себе не определяет, находится ли Rust в нём.

Задайте полный путь, подставив настоящее имя `.app`:

```sh
PATCH_REVIEW_BINARY="$PATCH_REVIEW_DIR/new/Payload/Telegram.app/Frameworks/TelegramCoreFramework.framework/TelegramCoreFramework"
file "$PATCH_REVIEW_BINARY"
xcrun lipo -info "$PATCH_REVIEW_BINARY"
xcrun otool -l "$PATCH_REVIEW_BINARY" > "$PATCH_REVIEW_DIR/load-commands.txt"
```

В `load-commands.txt` смотрите архитектуру и `LC_ENCRYPTION_INFO` /
`LC_ENCRYPTION_INFO_64`, если они есть. `cryptid`, отличный от нуля, означает
зашифрованный образ. Генераторы также проверяют это сами.

### Получить текст инструкций

Для thin arm64 Mach-O:

```sh
xcrun llvm-objdump --disassemble "$PATCH_REVIEW_BINARY" \
  > "$PATCH_REVIEW_DIR/new-disassembly.txt"
```

Альтернатива через `otool`:

```sh
xcrun otool -arch arm64 -tvV "$PATCH_REVIEW_BINARY" \
  > "$PATCH_REVIEW_DIR/new-disassembly.txt"
```

Точно так же получите `old-disassembly.txt` из старого файла. Если известны
VA начала и конца нужного участка, вывод LLVM можно ограничить:

```sh
xcrun llvm-objdump --disassemble \
  --start-address=0x100001000 --stop-address=0x100001100 \
  "$PATCH_REVIEW_BINARY"
```

Адреса в этой команде **учебные**. Замените их адресами исследуемой функции.
Верхняя граница не включается. Параметры описаны в
[документации llvm-objdump](https://llvm.org/docs/CommandGuide/llvm-objdump.html).

### Найти соответствующую функцию

Начните с определения того, на какой проверке остановился генератор. Например,
ошибка `native TL constructor` указывает на `REVIEWED['constructor']` в
`Tools/prepare_native_tl.py`. Для старой IPA текущий генератор позволяет
однозначно найти эту функцию и её вызовы.

В новой версии ищите кандидата по нескольким признакам:

1. Сохранённые символы или метаданные типа Swift, если они присутствуют.
2. Характерные строки, которые использует функция, и ссылки на них из кода.
3. Функции, которые её вызывают, и функции, которые вызывает она.
4. Последовательность проверок, работа с полями и обработка ошибок.

Например, Rust-генератор использует маркер
`[MTProtoRust] mt_engine_create failed` и проверяет инициализацию сессии.
Pro находится через метаданные `TelegramUIPreferences.SGStatus` и соответствие
`Swift.Decodable`. Эти признаки помогают найти кандидата, но не заменяют
проверку его команд и ABI.

Если имён функций нет, это нормально: релизные сборки часто удаляют символы.
Поиск только по строке в `strings` не покажет вызывающую её функцию: нужна
ссылка на строку из кода. Для сложного случая удобно использовать дизассемблер
с перекрёстными ссылками и декомпилятором. Псевдокод помогает понять назначение,
но регистры и точку вставки всё равно проверяйте по реальным инструкциям.

### Сравнить смысл и ABI

Составьте небольшую таблицу для каждой изменившейся функции:

| Вопрос | Что записать |
| --- | --- |
| Какова роль функции | Например, входящее удаление сообщений, а не любое удаление |
| Где её начало и конец | VA и размер в байтах; наличие нескольких выходов |
| Где находятся аргументы | Регистры, стек, контекст аккаунта, указатель транзакции |
| Куда идёт исходный вызов | Проверенная функция либо конкретный импорт и библиотека |
| Как возвращается результат | Значение, косвенная запись, optional, состояние ошибки |
| Кто владеет памятью | Кто удерживает, копирует и освобождает объекты или буферы |
| Что меняет патч | Конкретная инструкция и ожидаемое поведение |
| Что сохраняет адаптер | Нужные регистры, стек, исходный вызов и путь ошибки |

Одинаковый размер функции не означает одинаковое поведение. Изменившийся размер
не обязательно означает изменение ABI, но требует проверить весь существенный
путь выполнения. При появлении дополнительных вызовов разберите их назначение
до изменения ожидаемого количества.

Если пока не получается ответить, где аргументы и куда возвращается управление,
сохраните дизассемблирование, сведения об IPA и свои наблюдения для разработчика,
который знаком с ARM64. Проверка этих пунктов — обязательная часть ручного переноса.

### Вычислить отпечаток проверенной функции

После разбора можно вычислить оба вида отпечатка инструментами проекта:

```sh
python3 - "$PATCH_REVIEW_BINARY" 0x100001000 0x100001100 <<'PY'
import json
from pathlib import Path
import sys

sys.path.insert(0, str(Path('Tools/RustBridge').resolve()))
from macho import MachO

image = MachO(Path(sys.argv[1]).read_bytes())
start, end = (int(value, 0) for value in sys.argv[2:4])
assert start < end and (end - start) % 4 == 0
assert image.function(start) == (start, end), 'Проверьте границы функции'
print('review:', image.fingerprint(start, end))
print('portable:', json.dumps(image.portable_fingerprint(start, end), indent=2))
PY
```

Здесь снова указаны учебные VA. Используйте реальные границы в модели
`MachO` проекта. Метод `function()` опирается на таблицу начал функций Mach-O;
не обрезайте диапазон произвольно ради получения совпадения.

Команда **ничего не записывает в профили**. Она лишь вычисляет значения для
уже проверенного кода. Решение о добавлении нового отпечатка зависит от разбора
функции, её вызовов и ABI.

## Обновление каждого семейства патчей

Прямые генераторы ниже предназначены для отдельного исследования. В отличие
от общего `update_patches.py`, они могут записывать файлы по ходу работы.
Запускайте их в подготовленной ветке и проверяйте diff даже после ошибки.

### Native TL Decoder

Исходники и проверки:

- `Tools/prepare_native_tl.py`, таблица `REVIEWED` и функция `identify()`;
- `Patches/native-tl-v1/payloads/constructor.c` и `result.c`;
- `Sources/tgapiC/NativeTLProfile.inc` и код Native TL в `Sources/tgapiC`.

Проверяются четыре функции: `constructor`, `body`, `result`, `topLevel`.
Важно подтвердить не только сами парсеры, но и их расположение в проверяемой
группе функций. Вызов конструктора из верхней Swift-обёртки и вызов
function-result перенаправляются по одному; рекурсивные native-вызовы
не должны случайно попасть под те же перехваты.

Для совместимого кода:

```sh
python3 Tools/prepare_native_tl.py packages/Telegram_new.ipa
python3 Tools/prepare_native_tl.py packages/Swiftgram_new.ipa --check
```

Первая команда создаёт профиль и runtime matcher. Вторая проверяет, что этот
же результат подходит Swiftgram. Если второй клиент даёт другой результат,
перезапись общих файлов по очереди не создаст поддержку обоих клиентов.

При изменившемся коде сначала проверьте сигнатуры парсеров и правила владения
объектами, затем обновляйте reviewed-данные и генератор. Если нужно поддержать
несколько разных реализаций одновременно, потребуется расширить представление
профилей и runtime matcher; текущая таблица не является автоматическим списком
всех версий.

Правила обработки полей сообщений находятся в
`Sources/tgapi/TL/MessagePatches.swift`. Их не требуется переносить в машинный
код при обновлении адресов парсера.

После изменения `NativeTLProfile.inc` пересоберите сам TGExtra DEB.

### Rust MTProto Bridge

Исходники и проверки:

- `Tools/RustBridge/abi5.json` — reviewed-признаки функций;
- `Tools/prepare_rust_patch.py` — распознавание и проверки интеграции;
- `Tools/RustBridge/portable.py` — генерация переносимого профиля;
- `Sources/tgapi/RustBridge.h` и `.m` — контракт и реализация runtime;
- [описание Rust bridge](../Tools/RustBridge/README.md).

Текущие профили рассчитаны на **C ABI 5** Rust engine. Проверяются также
аллокатор request ID, работа с буферами, инициализация сессии, привязка
контекста и ожидаемые вызовы. Изменения времени жизни сессии или освобождения
буфера могут давать сбой позже, даже если простой запрос успешно отправился.

Для совместимого клиента:

```sh
python3 Tools/prepare_rust_patch.py \
  packages/Telegram_new.ipa packages/Telegram-rust.ipatch \
  --patch-set-dir Patches \
  --engine "$IPATCH_ENGINE_CLI" \
  --plan-file packages/Telegram-rust-plan.json
```

Повторите для Swiftgram с его именами. Эти отдельные Rust-архивы предназначены
для проверки bridge; полный пакет TGExtra собирайте через `package_ipatch.py`
с DEB и всеми профилями.

Каталог профиля получает идентификатор из содержимого профиля и адаптеров.
Не вычисляйте имя из хеша IPA и не переименовывайте его вручную.
Отличие консервативного отпечатка между Telegram и Swiftgram может требовать
разных профилей при одинаковом ABI.

Показательный случай уже описан в Rust README: четыре записи глобальных
переменных внутри `engineCreate` имеют page offset `0xb8` у Telegram и `0x4b8`
у Swiftgram. Допуск второго варианта основан на разборе соответствующих
`ADRP`, загрузок, записей и ветвлений. Это не общее разрешение игнорировать
любые изменившиеся смещения.

Если ABI действительно изменился, недостаточно добавить новый хеш в
`abi5.json`. Потребуется проверить и при необходимости изменить адаптеры,
сигнатуры и runtime, а также способ представления нового ABI в генераторе.
Не объявляйте неизвестный ABI совместимым с ABI 5 по одному похожему фрагменту.

### Secret Chat Protection

Исходники и проверки:

- `Tools/SecretChats/reviewed.json` — отпечатки, смещения вызовов и доказательства исходных целей;
- `Tools/prepare_secret_chats.py` — проверка входов и таблица `GATES`;
- `Tools/SecretChats/gate.c.in` — шаблон сохранения регистров и вызова callback;
- `Sources/tgapi/SecretChatPolicy.swift` и связанные обработчики.

Пять точек перехвата отвечают за уведомление о скриншоте, входящее удаление,
входящую очистку истории, проверку истечения таймера и потребления медиа.
Нужно подтвердить, что это именно нужные действия: локальное удаление
пользователем должно оставаться доступным.

Для совместимых клиентов:

```sh
python3 Tools/prepare_secret_chats.py \
  --telegram packages/Telegram_new.ipa \
  --swiftgram packages/Swiftgram_new.ipa
python3 Tools/build_payloads.py
```

При ручном обновлении для каждого вызова проверьте:

1. Функцию, внутри которой находится вызов, и его новое смещение.
2. Тип перехода `b` или `bl` и исходную цель.
3. Отпечаток исходной функции либо точные байты импортного stub.
4. Для stub — реальную chained-привязку, имя символа и install name библиотеки.
5. Расположение аргументов, включая транзакцию, ID сообщений и поля идентичности.
6. Поведение при блокировке и при отсутствии callback TGExtra.

Caller, то есть вызывающая функция, может остаться прежней, а импортная
привязка измениться. Поэтому одного совпадения отпечатка caller недостаточно.
Иное значение GOT ordinal также требует проверить реальную привязку.

Шаблон сохраняет `x0`–`x8`, `x20`, `x21` и другие используемые сохранения,
восстанавливает стек перед исходным вызовом. Числа в `[sp, #...]` зависят
от расположения сохранённых значений. Если поменять размер сохранений,
таблица извлечения аргументов тоже может потребовать изменения.

Редактируйте `gate.c.in` и таблицу `GATES`, затем запускайте
`build_payloads.py`. Правки только сгенерированного `payloads/*.c` будут
перезаписаны. `build_payloads.py --check` проверяет также актуальность этих C-файлов.

Успешная блокировка входящего удаления должна сохранять обработку и
подтверждение входящих операций. Для таймеров важны учёт конкретного сообщения
и последующая очистка после выключения защиты. Простое удаление вызова может
нарушить эти условия.

### Swiftgram Pro

Этот профиль не имеет генератора, который переносит изменившийся код.
Общий updater лишь пересобирает имеющийся адаптер и проверяет прежний профиль
движком с включённым Pro.

Исходники и проверки:

- `Patches/swiftgram-pro-status-v1/patch.json`;
- `Patches/swiftgram-pro-status-v1/payloads/status.c`;
- `Tests/swiftgram_pro_ipatch.py`.

Профиль ищет структуру `TelegramUIPreferences.SGStatus` с единственным
изменяемым полем `status: Swift.Int64`, без generic-параметров, затем
единственное безусловное соответствие `Swift.Decodable` и witness
`init(from:)`. **Witness** здесь — функция, через которую тип выполняет
требование протокола.

Далее проверяются отпечатки 40-байтового witness и 268-байтового тела декодера.
В проверенной версии исходный декодер вызывается на смещении `+16`,
на `+20` проверяется ошибка, на `+24` сохраняется результат, а с `+28`
начинается общий выход из функции.

Существенная часть исходного потока управления:

```asm
mov  x19, x8          // сохранить адрес выходного значения
bl   decodeBody      // получить status в x0, состояние ошибки в x21
cbnz x21, epilogue   // при ошибке пропустить сохранение результата
str  x0, [x19]       // сохранить status при успехе
epilogue:
                     // восстановление сохранённых регистров и возврат
```

Комментарии объясняют проверенную функцию; они не задают правила для любого
Swift-декодера. Патч заменяет только `str x0, [x19]` на переход к адаптеру:

```asm
mov  x8, #2
cmp  x0, x8
csel x0, x0, x8, ge
str  x0, [x19]
b    epilogue
```

Его смысл — сохранить signed `max(2, status)`. Последний переход связывается
движком с `decode + 28` через relocation. В C-исходнике на его месте стоит
`b .`: при сборке итогового патча движок заменяет этот переход. Нельзя вставлять
сырые 20 байт в IPA без этой привязки.

Примеры результата при успешном декодировании:

| Входной status | Сохраняемый status |
| --- | --- |
| `-1` | `2` |
| `0` | `2` |
| `1` | `2` |
| `2` | `2` |
| `5` | `5` |

При ошибке декодирования запись результата должна остаться пропущенной.
Именно поэтому нельзя просто заменить вызов декодера на безусловный возврат 2.

Для новой версии нужно заново подтвердить тип поля, метаданные соответствия,
точку успешной записи, значения `x0`, `x19`, `x21`, допустимость использования
`x8`, положение эпилога и сохранение стека. Если схема изменилась, старые
`+24`, `+28`, размер 20 байт и размеры проверяемых функций не становятся
правильными автоматически.

Адаптер вставлен внутрь чужой Swift-функции. Обычная C-функция добавит свой
порядок работы со стеком и возвратом. Поэтому здесь используется
`__attribute__((naked))` с явными командами. Изменение этого места требует
соответствующего теста ABI и пути ошибки.

Если добавляется новая поддерживаемая реализация при сохранении старой,
оформите отдельный проверенный вариант или профиль с различимыми условиями.
Проверьте, что движок не применяет две альтернативные реализации к одной точке
при политике `all_matching`.

Проверка Pro на выбранной IPA:

```sh
IPATCH_ENGINE_CLI="$IPATCH_ENGINE_CLI" \
SWIFTGRAM_REFERENCE_IPA="$PWD/packages/Swiftgram_new.ipa" \
python3 Tests/swiftgram_pro_ipatch.py
```

Тест исполнения адаптера требует Apple Silicon. Если меняется сам witness,
его тестовый образ также должен соответствовать новой проверенной реализации.
Обновление ожидаемых значений теста должно следовать из разбора кода.

Pro-профиль меняет локальное поведение Swiftgram. Telegram Premium и серверные
возможности он не предоставляет. Поддержать автора Swiftgram можно официальной
покупкой Pro.

## Проверка на устройстве

Успешный план подтверждает совпадение структурных проверок и возможность
построить изменения. Проверка на iPhone нужна для поведения в реальном клиенте.
Для сравнительных действий удобно использовать отдельный тестовый чат и
второй аккаунт или устройство.

Запишите версию клиента, build number, iOS, модель устройства, commit TGExtra,
вариант DEB и состояние Pro. После установки полностью перезапустите приложение.
Откройте **Настройки → TGExtra → Данные сообщений → Debug Log**
и сохраните сведения о схеме, hooks и callbacks.

| Область | Что проверить |
| --- | --- |
| Базовая работа | Запуск, получение и отправка сообщений, смена аккаунта, повторный запуск |
| Native TL | Обычные ответы и обновления; действие изменяемых политик; состояние интеграции в журнале |
| Rust | Отправка запросов, ghost mode, передача медиа и восстановление protected-forward; работа после переключения аккаунта |
| Секретные скриншоты | Наличие скриншота и ожидаемое отсутствие уведомления у второго участника при включённой защите |
| Входящие удаления | Удаление отдельного сообщения и очистка истории вторым участником; сохранение сообщений и меток |
| Локальное удаление | Собственное удаление и очистка истории продолжают работать |
| Таймеры | Истечение при включённой защите; после выключения — очистка для активного аккаунта в пределах цикла примерно 30 секунд; повторить после перезапуска |
| Потребление медиа | Поведение исчезающих фото и видео и сохранения при соответствующих настройках |
| Pro | Сравнение двух IPA из одного оригинала: Pro выключен и включён; инициализация статуса нового аккаунта после онлайн-запуска |

Проверяйте функцию также с выключенным переключателем: новое поведение должно
зависеть от настройки там, где это предусмотрено. Для приватности проверка
со стороны второго участника показывает больше, чем состояние кнопки на экране.

При падении сохраните crash log, Debug Log и точную последовательность действий.
Если функция не вызывается в простом сценарии, отсутствие падения не проверяет
её адаптер. Для возврата используйте ранее проверенные исходники, соответствующий
DEB и оригинальную IPA; не накладывайте старый пакет поверх уже изменённой IPA.

## Что сохранить в Git

Перед коммитом:

```sh
git status --short
git diff --check
git diff --stat
```

В изменение обычно входят профили JSON, исходники C и, при соответствующих
изменениях, генераторы, reviewed-данные, runtime matcher, runtime-код и тесты.
Сгенерированные `.bin` игнорируются: релизная сборка создаёт их заново.

Не добавляйте IPA, DEB, локальные планы и распакованные приложения.
Для индексации используйте явные пути к проверенным изменениям. Старые
Rust-профили сохраняйте, если их поддержка остаётся заявленной.

В описании изменения укажите:

- Точные версии, build numbers и bundle IDs новых клиентов.
- Какие семейства проверены и где потребовалось изменение кода или ABI.
- Почему новые отпечатки и смещения соответствуют нужным функциям.
- Результаты тестов, проверки плана и применения к новой IPA.
- Что выполнено на устройстве, с какими настройками и аккаунтами.
- Какие проверки пропущены и какая совместимость со старыми сборками сохранена.

Обновите сведения о поддерживаемых сборках в основном README и
[техническом описании профилей](README.md). Добавление IPA в список эталонов
должно сопровождаться реальной проверкой этой сборки.

## Краткая памятка

Обычный цикл при совместимом коде:

```sh
export IPATCH_ENGINE_CLI="$HOME/Tools/ipatch"

python3 Tools/update_patches.py \
  --telegram packages/Telegram_new.ipa \
  --swiftgram packages/Swiftgram_new.ipa \
  --engine "$IPATCH_ENGINE_CLI"

git diff -- Patches Sources/tgapiC/NativeTLProfile.inc

python3 Tools/update_patches.py \
  --telegram packages/Telegram_new.ipa \
  --swiftgram packages/Swiftgram_new.ipa \
  --engine "$IPATCH_ENGINE_CLI" --check

export SWIFTGRAM_REFERENCE_IPA="$PWD/packages/Swiftgram_new.ipa"
bash Tests/run.sh
```

Затем соберите ipatch с соответствующим DEB, проверьте полный пакет на обеих
новых IPA, отдельно включите Pro в его проверке, примените патчи к копиям и
выполните сценарии на устройстве. Если распознавание кода остановилось,
вернитесь к разбору нужного семейства перед дальнейшей сборкой.
